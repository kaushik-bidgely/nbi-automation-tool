## Stack

- **Backend:** FastAPI + SQLAlchemy + SQLite (`backend/app/`). `nbi_tool.db` is the SQLite file — no Alembic/migrations. **As of 2026-07-22, do NOT reseed to pick up a schema change** (`rm nbi_tool.db && python -m app.seed`) — the local DB now holds real, non-reproducible data (Pilot A–E content, the 6 real+seeded accounts, live Interaction records) that reseeding would destroy. ## Core architecture — read before changing permissions or the content model

**Three roles:** `admin` (full access), `tpm_csm` (content-edit), `utility` (external, scoped per-account via `User.allowed_pilot_ids`/`content_scope`/`channel_scope`). **No longer read-only as of 2026-07-22** — see "Utility edit rights" below.

**Utility edit rights** (added 2026-07-22, real access-control change, not just UI): utility can now `edit` exactly 9 fields — the ones already rendered as editable columns in the condensed Actions/Insights tables (`ActionItem`: `description`, `subject_line_email`, `footer_disclaimer`, `short_desc`, `title`; `InsightItem`: `subject_line`, `insight_text`, `insight_semantic`, `paper_text` — see `rbac_matrix.py`). Everything else utility can see (`appliance`, image fields, `cta_text`/`cta_link_name`/`subject_title_paper`) stays `view` — deliberately, since utility has no route to the full editor where those are edited. Three things had to change together for this to actually work, not just the matrix:
- `backend/app/permissions.py`'s `action_editable_fields`/`insight_editable_fields` now take an optional `channel_scope` param — without it, `resolve_permissions` zeroes out every channel-gated field for utility regardless of matrix permission (channel-gating only activates when `channel_scope` is actually passed). A utility account scoped to `channel_scope="paper"` can edit `short_desc`/`title` but gets a 403 on `description` even though the role-level permission says `edit`.
- `backend/app/main.py`'s generic `PATCH /api/actions/{id}`/`/insights/{id}` no longer call `require_not_utility` — they call `check_pilot_access(user, obj.pilot_id, "actions"/"insights")` instead (same helper `submit_action` already used), so utility is scoped by `allowed_pilot_ids`/`content_scope` like every other utility-accessible endpoint, and `action_editable_fields(user.role, user.channel_scope)` now gets the channel_scope argument.
- Frontend: `UtilityContentView.tsx` (a separate, simpler read-only component) is deleted — utility now renders the exact same `ActionsList.tsx`/`InsightsList.tsx` condensed table as admin/tpm_csm. Editability already worked generically off the permissions map with zero utility-specific code once the backend changed. The one thing added: the "Open full editor" icon-link (which would navigate to the full `ActionEditor`/`InsightEditor` page) is hidden for `role === "utility"` — that page stays admin/tpm_csm-only, its route was already `{role !== "utility" && ...}`-gated in `App.tsx` and still is.
- Unchanged, deliberately: `/validate`, `/unlock`, and every Interaction endpoint still block utility entirely (`require_not_utility`/`require_role`) — Interactions access was explicitly *not* extended to utility.

**Two content entities**, `ActionItem` and `InsightItem` (`backend/app/models.py`), each belonging to a `Pilot`. `(pilot_id, action_id)`/`(pilot_id, insight_id)` are unique together — the same natural-key code can exist in multiple pilots.

**Field-level permissions are defined in exactly one place: `backend/app/rbac_matrix.py`.** Every field has a `category` (`content`/`image`/`internal`/`generated`) and a per-role permission (`edit`/`view`/`none`). `backend/app/permissions.py`'s functions are thin resolvers over this file — don't hand-edit permission sets anywhere else. The frontend has no local copy of these rules; it fetches `GET /api/permissions/actions` / `/insights` and renders from that (see `AuthContext.tsx`'s `usePermissions` hook). If you add a new field to `ActionItem`/`InsightItem`, you must add a matching `FieldRule` to `rbac_matrix.py` or it won't appear in any API response for any role.

**Content lifecycle** (independent of role permissions above): `draft → ready_for_qa → published → modified → ready_for_qa`. Transitions live in `main.py` as dedicated endpoints (`/submit`, `/unlock`, `/publish`), not the generic `PATCH` — the generic update endpoint blocks all edits to a `published` item until `/unlock` is called. As of 2026-07-17, the generic `PATCH` also has one side effect: editing any field on a `ready_for_qa` item silently reverts its status back to `draft` (never touches `modified`/`published`) — an edit invalidates whatever QA review already happened. The Actions/Insights list tables' Status column is an interactive dropdown (not just a display chip) — selecting "Ready for QA" there calls the same `/submit` endpoint as the existing checkbox+bulk-button flow, just per-row. **As of 2026-07-22, `InteractionRecord` shares this exact same 4-status lifecycle** (see "Interactions" below) — it used to have its own unrelated `merged`/`exported` status, replaced entirely.

**Char limits gate Save, not just show a warning** (fixed 2026-07-22): only 3 fields have a real limit sourced from the master spreadsheet's own column headers — Actions `short_desc` ≤110, `title` ≤55; Insights `insight_semantic` ≤135 (`frontend/src/fieldGroups.ts`'s `ACTION_CHAR_LIMITS`/`INSIGHT_CHAR_LIMITS`). `EditableCell` already showed an error style over the limit, but the row-level Save button didn't actually block on it — `ActionRow`/`InsightRow` now compute `overLimit` from `dirty` against those maps and disable Save (with a tooltip) when any dirty field is over. Deliberately did **not** add new limits to other free-text fields (email body, footer disclaimer, subject lines, insight text, paper text, the 3 Interaction override fields) — there's no source-of-truth number for those, confirmed with Kaushik rather than inventing one.

**Schema Reference page** (`/schema`, admin-only, added 2026-07-17, Interactions tab added 2026-07-22): a read-only view of every Action/Insight/Interaction field's category, channel, type, accepted values, and a hand-authored description. Actions/Insights are assembled live from `rbac_matrix.py`/`tag_logic.py`/`sheet_export.py`/`validation.py`/SQLAlchemy column introspection, never a separate copy that could drift. Interactions have no `rbac_matrix.py` equivalent (no per-field/per-role permission split — the whole entity is admin-edit/tpm_csm-view/utility-none, and most fields are computed rather than real columns), so `get_interaction_schema()` is hand-authored against `interaction_logic.FIELDS` with an `assert` guarding against drift — see `schema_reference.py`. Deliberately not editable through the UI — to change a value/vocab, edit the backend code, same git-reviewable-diff principle as `rbac_matrix.py` itself. Also flags which fields exist in the schema but aren't actually rendered anywhere in the app (currently just `updated_at`, via the hand-maintained `FIELDS_NOT_SHOWN_IN_UI` set — update that set if a UI change adds/drops a field's visibility).

**Pilots admin page** (`/pilots`, admin-only, added 2026-07-22): lists every pilot with "Upload Actions"/"Upload Insights"/"Upload Interactions" buttons, calling the pilot-scoped `POST /api/pilots/{pilot_id}/upload/actions|insights|interactions` endpoints. Actions/Insights upserts by `(pilot_id, action_id/insight_id)`, skips anything already Published — these two endpoints pre-existed (previously only reachable from the Create Pilot dialog at creation time; this page just added a UI entry point for re-uploading onto an *existing* pilot). Interactions upload (`backend/app/interaction_import.py`, new 2026-07-22) is new: accepts a CSV in the same 20-column schema this app's own Interaction export produces, resolves each row's `insight_id`/`action_id` against the pilot's existing Actions/Insights (stripping a `_S`/`_W` suffix and validating it's a real seasonal variant via `interaction_logic.seasonal_variant_for` when present), and upserts an `InteractionRecord` with the 3 content fields stored as that interaction's overrides. **"Create Pilot" now lives on this page** (moved off the top-bar pilot dropdown, which no longer has a "+ Create new pilot…" option) — `CreatePilotDialog.tsx` also gained an optional 3rd file input for an Interactions sheet alongside Actions/Insights when creating via upload rather than clone-from-master.

**Nav tabs are hidden per-pilot when that pilot has none of that content yet — for `tpm_csm`/`utility` only** (added 2026-07-22, narrowed same day). `Pilot.action_count`/`insight_count`/`interaction_count` (computed properties on the model, `len()` over the relevant relationship — see `models.py`) are returned by `GET /api/pilots` and feed `App.tsx`'s `showActions`/`showInsights`/`showInteractions`. **Admin always sees all 3 tabs (and the Dashboard quick-link) regardless of count** — the initial version hid them for everyone including admin, which meant an admin landing on a freshly created empty pilot had no way to *discover* it needed content, and literally couldn't reach Interactions to create the first one (Merge All / upload) since the nav link to get there was hidden. Fixed same day: `showInteractions = role === "admin"` unconditionally; `showActions`/`showInsights` are `role === "admin" || (previous role/content_scope-gated check)`.

**Interactions are a separate concept from Action/Insight identity, but as of 2026-07-22 share their exact status lifecycle** (renamed from "Merge" 2026-07-22). An `InteractionRecord` pairs one Action with one Insight (Admin-only). Merging/un-merging never changes the *linked Action/Insight's* status; whether something is merged is a computed `merged` property on ActionItem/InsightItem (checks for an `InteractionRecord`), not a stored flag — separate from the Interaction's *own* `draft/ready_for_qa/published/modified` status. Two ways to create one:
- **Manual** — `POST /api/interactions` (single action_item_id + insight_item_id), gated by the lightweight `validation.validate_pairing` (appliance + fuel type match only). Starts at `draft`.
- **Bulk** — `POST /api/pilots/{pilot_id}/interactions/bulk-merge`, which runs `backend/app/interaction_logic.py`: a deliberate 1:1 port of PE's real `generate_nbi_configs.py` (`bidgely/pingpong`, `dev-tools/src/main/python/`) — same `apply_rules` pairing logic (fuel+appliance match, extra-tags compatibility, "tou" symmetry, Program/dollar-insight rule, prod/generic exclusion — including its currently-inactive commented-out branches, kept inactive on purpose) and the same `add_seasonal_actions` synthetic-seasonal-variant behavior (an `ac`/`sh`-appliance action of nbi_type "Actionable Reco tip"/"Program" gets a second, "SummerSeasonal"/"WinterSeasonal"/"SummerProgram"/"WinterProgram" pairing — represented as a second `InteractionRecord` with `seasonal_suffix` set to `"S"`/`"W"`, not a second `ActionItem` row). Creates immediately (all at `draft`), no preview/dry-run step, by design.
- **Status lifecycle** (added 2026-07-22, replacing the old `merged`/`exported` status): `POST /api/interactions/{id}/submit` (draft/modified → ready_for_qa), `POST /api/pilots/{pilot_id}/interactions/publish` (bulk, ready_for_qa → published, admin-only, mirrors `publish_actions`/`publish_insights` incl. returning a CSV of just the newly-published rows), `POST /api/interactions/{id}/unlock` (published → modified). The generic `PATCH /api/interactions/{id}` blocks edits on a `published` interaction (409, same as Actions/Insights) and reverts `ready_for_qa` → `draft` on any actual override edit. All existing `merged`/`exported` rows were one-time-migrated to `draft` when this shipped.
- `InteractionRecord` carries 3 per-interaction overrides (`action_text_override`, `insight_semantic_override`, `insight_text_override`) — editable independently per pairing without touching the shared Action/Insight; unset (`None`) means "still tracking the live source value." **There's currently no way to clear an override back to `None`** once set (the `PATCH` endpoint only sets non-null values) — a real gap if that's ever needed.
- `interaction_logic.compute_fields()` is the single source of truth for the PE 20-column schema (`nbi_id, insight_id, action_id, insight_semantic, insight_text, action, tag_insight, tag_action, tag_generic, tag_objective, var_i_name, filter_utility, filter_ownership, filter_season, nbi_family, nbi_type, nbi_fuel_type, nbi_appliance, min, max`) — used by both the API response (`InteractionOut`) and CSV export. `filter_utility` is always blank — the real script hardcodes it, it's not derived from anything.
- Validated 2026-07-22 against a real reference file (`~/Downloads/Old NBIs Analysis.xlsx`'s "PE Script Output" sheet, 1446 real rows): 94% of pairs match exactly; the rest is explained by data drift since that reference was generated (e.g. some Lighting insights now store `appliance="lt"` instead of `"li"` — the same pre-existing inconsistency already noted in the CSV-export quirk below), not a bug in the port.
- Frontend: `frontend/src/pages/InteractionsView.tsx` (renamed from `MergeView.tsx`) — paginated table (interactions can run into the thousands per pilot), checkbox selection + "Move to Ready for QA"/"Publish Selected" bulk buttons (mirrors ActionsList/InsightsList), a per-row Status dropdown (locks the 3 editable cells + shows an Unlock button once Published), and both the manual picker and "Merge All" button. The NBI ID cell itself is the clickable trigger for the "detail dialog" (other 14 read-only fields) — there's no separate info icon (removed 2026-07-22 in favor of making the id text itself the link).

**Interaction sheet upload** (`backend/app/interaction_import.py`, new 2026-07-22): accepts a CSV in the same 20-column schema as the Interaction export/PE reference format, resolves each row's `insight_id`/`action_id` against the pilot's existing Actions/Insights (stripping a `_S`/`_W` suffix and validating it via `interaction_logic.seasonal_variant_for` when present), and upserts an `InteractionRecord` (new rows start at `draft`) with the 3 content fields stored as that interaction's overrides. Wired to `POST /api/pilots/{pilot_id}/upload/interactions` and the Pilots admin page's "Upload Interactions" button.

**Sheet upload error handling** (fixed 2026-07-23 — was a real bug, not a hypothetical): `import_actions`/`import_insights`/`import_interactions` used to let a raw pandas/openpyxl exception (most commonly `ValueError: Worksheet named 'Actions' not found` — i.e. the uploaded file's sheet isn't named exactly `"Actions"`/`"Insights"`, or a CSV is missing `insight_id`/`action_id` columns) propagate all the way up as an unhandled exception, which FastAPI turned into an opaque `500 Internal Server Error` with no detail — the frontend then showed nothing useful, and (in `CreatePilotDialog.tsx` specifically) the pilot record from `createPilot` had already been committed, so retrying left an empty, code-blocking orphan pilot behind (`POST /api/pilots` would then 409 on the same code). Fixed: `sheet_import.py`/`interaction_import.py` now catch parse failures and raise `SheetFormatError` (a `ValueError` subclass) with a specific, actionable message; `main.py`'s `_import_or_422()` helper wraps all 3 upload endpoints, converting `SheetFormatError` (and any other exception, as a fallback) into a `422` with that message instead of a `500`. `CreatePilotDialog.tsx` now parses the JSON error detail the same way every other page already does (`ManageUsers.tsx`, `UtilityContentView`'s successor, etc.), and — new — deletes the just-created pilot if a subsequent clone/upload step fails, so the dialog stays usable for an immediate retry with the same code rather than requiring a new one.

**Sheet-name resolution relaxed** (2026-07-23, follow-up to the fix above — real UX gap, not the same bug): `import_actions`/`import_insights` used to hard-require the uploaded workbook's internal tab to be named exactly `"Actions"`/`"Insights"`, which meant a pilot-specific single-tab export (e.g. Excel/Sheets naming it `"Sheet1"`) always failed even though there was no real ambiguity about which sheet to read. New `_read_sheet()` helper in `sheet_import.py`: uses the exact-name match if present; otherwise, if the workbook has **only one sheet**, uses that sheet regardless of its name (nothing else it could be); otherwise raises `SheetFormatError` listing the sheet names found and asking the user to rename the right tab to `"Actions"`/`"Insights"`. Deliberately does **not** fall back to "first sheet" when there are multiple unnamed-correctly sheets — the real master workbook has several tabs (Steps, Resources, RBAC, etc. alongside the actual data), and silently guessing which one is intended risks importing the wrong sheet's data with no error at all, which is worse than today's clear failure. `CreatePilotDialog.tsx`'s upload-mode caption text updated to describe this. Interactions upload (CSV, no sheet concept) is unaffected. Verified via curl: a single-sheet workbook named arbitrarily now imports successfully end-to-end; a multi-sheet workbook with no `"Actions"`-named tab returns a 422 listing the actual sheet names found.

**CSV export** (`backend/app/sheet_export.py` for Actions/Insights; `interaction_logic.compute_fields`+`FIELDS` for Interactions) reconstructs the *original* master-sheet column layout (73 cols Actions / 102 cols Insights) or the 20-col PE schema from the structured fields — including replicating a known source-file quirk (Insights' "Lighting" flag column uses token `li` even though the identity column stores `lt`). Don't "fix" that — it's intentional fidelity to the real spreadsheet. `/publish` (Ready for QA → Published, admin-only, mutates status, all 3 entities) always produces a CSV of just what it published. **"Download Sheet"** (`/export` on all 3 entities, admin-only, no status change) is, as of 2026-07-22, status-filterable rather than fixed to "Ready for QA or later": `GET .../export?statuses=draft,ready_for_qa,...` (comma-separated subset of the 4 statuses; omitting the param keeps the old default of `ready_for_qa,published,modified`). The frontend's shared `frontend/src/DownloadSheetDialog.tsx` (checkboxes, defaults to that same 3-status set) is used by all three list pages' "Download Sheet" button — don't reimplement the status picker per page.

**Table UX: select-all, edit-vs-select mutual exclusion, and unsaved/over-limit cell highlighting** (2026-07-23): all 3 list tables (`ActionsList.tsx`, `InsightsList.tsx`, `InteractionsView.tsx`) gained a header checkbox that selects every currently-visible row (the filtered set for Actions/Insights; just the current page for Interactions, since that table can run into the thousands per pilot) — wired into the same `selected` Set the existing per-row checkboxes and bulk "Move to Ready for QA"/"Publish Selected" buttons already used, so no new bulk-action plumbing was needed. New rule: a selected row's content cells become read-only (`isEditable`/`editable` now also checks `!selected`) — selection is for bulk status moves, and editing a Ready-for-QA row silently reverts it to Draft, which would undermine a bulk transition in progress if left possible. `EditableCell.tsx` gained a `dirty?: boolean` prop: an unsaved (dirty) field now stays highlighted orange in its collapsed (non-editing) view, not just while the textarea has focus, using `alpha(theme.palette.warning.main, 0.08)` (matching `theme.ts`'s existing `alpha()` convention for tints, e.g. row hover/selected-toggle). Over-the-char-limit fields (Actions/Insights only — Interactions has no char limits) get the same persistent-after-blur treatment in red, and — the actual bug fixed here — the per-row Status `Select` is now also `disabled` when `overLimit` (previously only the Save button was gated, so a row over its char limit could still be moved to Ready for QA via the status dropdown, leaving unsaved-and-invalid content behind with no way to save it once submitted).

## Conventions established this session (follow these, don't relitigate them)

- Backend response filtering happens server-side for **every** role via `resolve_action_permissions`/`resolve_insight_permissions` + `filter_response` in `main.py` — never rely on the frontend to hide a field that a role shouldn't see at all.
- Frontend components (`FieldGroup.tsx`, `TagEditor.tsx`, list pages, editors) read editability from the permissions map (`permissions[field] === "edit"`), not from hardcoded role checks or TS constants. `frontend/src/fieldGroups.ts` holds only UI-layout metadata (channel groupings, char limits, tag vocab) — not permission data.
- Verification pattern used throughout: curl with real login tokens per role to check API-level enforcement, then browser click-through (via the preview/browser tools) per role to confirm UI behavior matches. Do both — API-only or UI-only checks have each missed real bugs in this project before.
- Before assuming a bug, check whether the backend has `--reload` running — a stale process has caused "my fix isn't working" confusion at least once. **`.claude/launch.json`'s `backend` config was itself missing `--reload` for most of this project's history** (fixed 2026-07-22) — if a fresh clone's launch config ever regresses on this, restart-after-every-backend-edit is the workaround.

## Security + correctness fix pass (2026-07-23)

Kaushik asked for a full "check everything" review after many feature-additive sessions. Three parallel audits (backend, frontend, DB/deployment-readiness) plus a design pass turned up one critical live vulnerability and several real bugs. Fixed, in scope order (deliberately excluded from this pass, per explicit confirmation: extending tpm_csm read access to Interactions — stays admin-only; the stale "utility read-only" label in `ManageUsers.tsx`; `tagPreview.ts`'s min/max prefix drift; a cosmetic colSpan off-by-one in Actions/InsightsList's empty state; `PilotContext`'s nav-tab staleness for non-admin roles; a stale status docstring in `schema_reference.py`):

- **CRITICAL — unauthenticated path traversal in the SPA-fallback route** (`backend/app/main.py`'s `serve_frontend`): `candidate = FRONTEND_DIST / full_path` had zero normalization/containment check, unlike the sibling `/assets` mount (which correctly uses Starlette's `StaticFiles`). Reproduced and confirmed exploitable: `curl --path-as-is "http://localhost:8000/../../backend/nbi_tool.db"` returned the live SQLite DB (every password hash, every session token) with HTTP 200, unauthenticated — same for reading `main.py`'s raw source. This is live the moment `frontend/dist` exists on disk (i.e. after any `build.sh` run — the documented Option A / unified-deployment path), not just in some hypothetical prod config. Fixed by resolving the candidate path and checking `is_relative_to(FRONTEND_DIST.resolve())` before serving it, falling through to `index.html` (not erroring) for anything outside — genuine SPA routes are unaffected. **If this repo has ever been exposed beyond localhost with `frontend/dist` built, treat `nbi_tool.db` (all password hashes + session tokens) as potentially already exfiltrated and rotate every password.**
- **Session invalidation on password change / user delete**: `update_user`/`delete_user` didn't touch the `sessions` table, so an old bearer token kept authenticating indefinitely (up to `SESSION_TTL_HOURS`) after a password rotation or account deletion. Both now delete the target user's `Session` rows (mirrors the existing `delete_pilot` query-then-delete pattern).
- **Interactions sheet-upload published-guard**: `interaction_import.py` used to overwrite a `published` interaction's overrides unconditionally on re-upload, bypassing the Unlock-first rule that `sheet_import.py` and the generic PATCH endpoint both already enforce. Now skips and counts them (`skipped_published`, surfaced in `PilotsAdmin.tsx`'s result message alongside `unmatched`), matching Actions/Insights exactly.
- **`ready_for_qa` → `draft` revert on sheet re-upload**: all 3 importers (`import_actions`/`import_insights`/`import_interactions`) now apply the same "an edit invalidates prior QA review" rule the generic PATCH endpoints already enforce — previously a sheet re-upload could silently rewrite a `ready_for_qa` row without forcing re-review.
- **Type-validated PATCH fields**: the generic `PATCH /api/actions|insights/{id}` only checked field *names* against the RBAC allow-list, never value *types* — `setattr(obj, field, value)` would happily write e.g. a raw string into a JSON-list column (`income_level`), corrupting `tag_string` and causing a `500` on the *next* read (response-model validation failing) — after the bad value was already committed. New `validation.ACTION_FIELD_TYPES`/`INSIGHT_FIELD_TYPES` + `validate_field_type()` (plain dicts, not introspection — matches this module's existing style) now reject a type mismatch with a `422` before anything is written; verified the DB value stays untouched on rejection.
- **Audit log for InteractionRecord**: `AuditLog.entity_type` documented `"interaction_record"` as valid, but none of the 7 interaction endpoints (create, bulk-merge, update, submit, unlock, publish, unmerge) ever called `log_change` — zero entries existed despite real status transitions having happened. All 7 now log, matching the exact pattern Actions/Insights already use (per-row logging inside bulk loops, a `status` entry for unmerge/delete as a deliberate, scoped addition since Action/Insight deletes still aren't logged anywhere).
- **`CreatePilotDialog.tsx` no longer discards partial successes**: previously, if e.g. Actions and Insights uploaded fine but Interactions failed, the *entire* pilot (including the successful imports) got deleted. Now only auto-deletes if nothing succeeded yet (same as before in that case); otherwise keeps the pilot and names which file(s) succeeded so just the failed one needs re-uploading via the Pilots page.
- Fixed as a side effect of the above: `backend/app/validation.py` was missing `from __future__ import annotations` — adding a `str | None` return-type annotation there (needed for the new `validate_field_type`) crashed the whole app at import time on this project's Python 3.9, since without postponed evaluation `|`-union syntax isn't valid pre-3.10. `main.py` already had this import for exactly this reason; `validation.py` didn't need it until now.
